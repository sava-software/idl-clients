# Fuzz seed corpora

Seed provenance lives here — next to, never inside, a corpus directory, where a
file would itself be fed to the harness as a seed. The replay test that runs
every seed inside `check` is generated by the sava-build hardening plugin
(`<Harness>SeedReplayTest`, one per target); each harness's contract is
documented on the harness class itself.

A corpus does two independent jobs. A **bootstrap** corpus buys coverage a
mutator would take too long to reach alone; a **regression** corpus is where a
finding lands, so a fixed crash stays fixed. "Every prefix of this format is
valid" answers only the first — every target here carries a corpus, and the
sections below say which job each one is doing.

## `stakePoolState/`

- `jito` — real mainnet Jito stake-pool account (611 bytes), fetched
  2026-07-16. Exercises the `Option`-steered offsets and `FutureEpochFee`
  branches that from-scratch inputs rarely assemble; the same account backs the
  `StakePoolStateTests` fixtures.

## `stakeAccount/`

- `116vkzEjoTpFEd3x12XL9HbYJ5EpoC4cZ9a1N5A5mUt` — real mainnet stake account
  (200 bytes, file name = account address), the same account behind
  `StakeAccountTests.parseRealStakeAccount`. It carries a fully-populated
  `Stake` state (authorities, delegation, credits), which a scratch mutator
  rarely assembles past the state-discriminant gate.

## `validatorList/`

Every prefix of this format is valid, so the mutator reaches it from scratch and
none of these are bootstraps — they are the regression slots, plus the two
shapes a scratch mutator produces only by accident:

- `jito-head-32` — the first 32 records of the real Jito validator list
  (`3R3nGZpQs2aZo5FDQvd2MUQ6R7KhAPainds6uT6uE2mn`, fetched 2026-07-25 with a
  2345-byte `dataSlice`), with the in-band count patched from 699 to the 32 the
  slice carries so the prefix is canonical. Real vote accounts, stake amounts
  and epochs; `maxValidators` is left at the live 10000, which the round trip
  does not require to equal the count.
- `status-spread` — the same real records, one per `StakeStatus` ordinal. The
  live list is 100% `Active`, so the deactivating/removal ordinals appear in no
  real dump.
- `empty` — the canonical 9-byte header with count 0.

## `precompileOffsets/`

A `u8` count with fixed 11/14-byte records: reachable from scratch, so these are
regression slots that also pin the shapes worth keeping in front of the parser.
One seed feeds all three parsers, so `data[0]` is the count each of them reads:

- `ed25519-single` — one signature laid out as `SignatureVerifyProgram` builds
  it (header `u8 count + u8 padding`, then the 14-byte offsets record pointing
  at an in-instruction key/signature/message).
- `secp256k1-two` — two signatures in the Secp256k1 layout (`u8 count`, no
  padding, 11-byte records whose instruction indexes are literal `u8`).
- `count-255-truncated` — the hostile case: a count of 255 against 200 bytes of
  payload, which must be rejected rather than read past the buffer.
- `zero-count` — a count of 0, whose parse must yield an empty array from all
  three.
